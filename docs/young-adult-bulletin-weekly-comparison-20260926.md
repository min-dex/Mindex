# 청년부 주보 7·8·9월 주차별 대조

검토일: 2026-09-26. 코드: `fc2915d5`.
사용자가 최종 지정한 핵심 기준은 **2026년 7·8·9월의 실제 주보 9개 / 18면**이다.
다른 시기는 참고 자료이며 현재 수정 우선순위에 과거 양식 전체 복원을 포함하지 않는다.

## 검증 범위

- 폴더의 PDF 72개 / 144쪽 텍스트와 앞뒷면 contact sheet를 확인한 뒤, 핵심 9호를 운영 DB 자료와 상세 대조했다.
- 7월 5·19·26일, 8월 2·16·23일, 9월 6·13·20일. 7/12 등 파일이 없는 날짜는 원본을 임의 생성하지 않았다.
- IDML은 9/20 한 개다. 다른 날짜는 PDF가 기준이다.
- 운영 DB의 service/section/element, 연결 song/scripture, calendar를 읽기 전용으로 조회했다. 숨김 상태·직접 성경 본문 필드도 포함했다.
- 로컬 Chromium에서 실제 앱의 `loadServiceBulletinSource → resolveSource → renderPages`를 실행하고 생성 18면도 contact sheet로 확인했다. 운영 응답을 로컬 데이터로 공급했으며 쓰기 요청은 없다.
- 비교 대상은 **수동 보정 없는 새 주보**다. `fields={}`, 기본 프레임, 자동 배경을 사용했다. 기존 저장 주보의 수정값·개인 브라우저의 자산 덮어쓰기·이전 주보의 공유 수정값은 적용하지 않았다.
- 전 호의 글자별 좌표나 픽셀 일치율을 측정한 결과는 아니다. 영역 경고, 내용 연결, 패널·로고·요점 구성, 월간/주간 변경을 비교했다.
- 원본·운영 DB·앱 코드는 변경하지 않았다. 중간 PDF·이미지·추출 텍스트는 메모리에서 처리했다. 남긴 파일은 이 보고서다.

### 원본을 그대로 규칙으로 만들면 안 되는 항목

- 9/20의 소식 번호 ①·①은 편집 중복이다. 자동 번호는 ①·②가 적절하다.
- 8/2 NEXT는 원본에서 당일 8/2에 표시되어 있다. 다른 호의 다음 주일 표시와 다르므로 이를 반복 규칙으로 만들지 않는다.
- 9/6 ‘통 128’과 DB의 ‘250’ 중 하나를 확인 없이 덮어쓰지 않는다. 원본도 오기가 있을 수 있다.
- 7/5 다음 주 광고는 교육사역부, DB 7/12 no_gathering_reason은 찬양사역부다. 서로 다른 자료의 확정 여부를 확인해야 한다.
- 7/5 찬양 4번째 곡, 8/2 수련회 상세 정보 누락, 8/16 태신자 제출 안내 추가는 원본과 DB 내용 자체의 차이다. 글꼴·레이아웃만 고쳐서 해결할 수 없다.

## 데이터 구조에 대한 결론

사용자가 제안한 **내용 데이터와 양식 데이터 두 축**을 유지할 수 있다.
새 테이블을 여러 개 만드는 것이 이번 대조의 결론은 아니다.

- **내용 데이터:** 공통 문구, 선택 월의 일정, 이번 주 예배/소식/요점, 발행 당시 확정된 위원표·순서 값.
- **양식 데이터:** 기간별 배경·로고·패널, 좌표·폰트·영역 크기, 요점 열 수와 표제 표시.
- 예배 자료 갱신은 명시적인 동작으로 처리하고, 발행 당시 내용이 최신 DB 조회 때문에 조용히 바뀌지 않게 한다.
- 사용자가 매주 입력할 것은 실제 자료에 없는 요점·누락 담당자·인쇄용 공지 보정이다. 이미 예배 DB에 있는 제목/본문을 저장 형식 차이 때문에 재입력하게 해서는 안 된다.

## 수정 순서

1. 예전 저장 형식의 설교 제목·본문·인용 인식, 중복 순서와 빈 안내 행 처리.
2. 원본에 근거한 담당자·기도 순서 연결, 달력의 예배 상태 표기, 발행 당시 값 보존.
3. 7·8월/9월의 주보 전용 양식 선택 및 로고·패널 일치.
4. 긴 소식과 두 열 요점 배치. 여백/좌표/폰트는 기존 2.5 단위 규칙 안에서 조정.
5. 동일 9호로 회귀 대조: 누락·중복·넘침과 원본 내용 차이를 각각 판정.
